# Architecture

## Current target

SmartSchool Manager is an offline-first Windows desktop application. The existing implementation is intentionally small: PyQt6 UI, SQLite persistence, and password helpers. Keep the UI thin as workflows grow; calculations and authorization belong in application services, while persistence and schema changes belong in the database layer.

## Proposed module boundaries

- `ui`: windows, dialogs, reusable widgets, and presentation-only validation.
- `services`: use cases, role checks, domain validation, transactions, and audit coordination.
- `repositories` / current `database`: parameterized persistence and migrations.
- `security`: password hashing, login throttling, and authorization policy primitives.
- `reporting`: PDF and tabular report composition.
- `integrations`: optional adapters that never gate offline workflows.

## Data and startup

The SQLite database remains under `%LOCALAPPDATA%\SmartSchoolManagerRebuild\school.db`; logs use the same app-specific directory. Startup configures logging, applies additive versioned migrations, checks foreign-key enforcement, then performs first-run setup and authentication. Migrations must back up an existing database and verify the backup before changing it. Tests must replace `DB_PATH` with a temporary location.

## Transaction rules

Multi-table business operations should run in one SQLite transaction. A failed operation rolls back. Session, term, and enrollment workflows authorize the active administrator and commit their audit entries in that same immediate transaction. Generic CRUD still logs changes separately and must be refactored before those actions are treated as reliable audit evidence.

## UI responsiveness

Keep authentication, database list queries and writes, student lookup, dashboard counts, and CSV export off the Qt UI thread. Render bounded pages (200 rows by default) and debounce free-text search. Discard stale worker results when a newer query has started. Keep pagination counts and result rows in one read transaction. Benchmark startup, search, paging, enrollment lookup, writes, and export with large synthetic datasets on a low-spec Windows device before setting performance targets. Avoid moving SQLite connections between threads; each database operation opens and closes its own connection.

## Academic calendar data

Schema version 2 stores academic sessions by unique name and terms by session, with a unique positive order within each session. At most one session can be marked current. Schema version 3 adds enrollment-history rows linking a student to an existing class/section and academic session. One active enrollment per student/session is allowed; transfers close the previous row and create a new row in one transaction. Completion and withdrawal also close rows without deleting history. Schema version 4 adds a unique class/subject assignment per academic session and allows an optional active teacher. Schema version 5 adds ordered, term-scoped assessment component definitions with maximum points stored as canonical decimal text. Schema version 6 adds an explicit Primary or Secondary stage to classes; existing classes remain unclassified and must be assigned by an administrator. Schema version 7 adds editable grade thresholds scoped to an academic session and stage; it does not seed grading scales or connect thresholds to calculated results. Schema version 8 adds daily attendance registers, explicit present/absent marks, and append-only correction history. Schema version 9 adds timetable slots tied to existing session-specific class-subject assignments, with explicit weekday and times and optional location. Service validation prevents class, assigned-teacher, and named-location overlap on the same day. No period lengths, school week, or bells are assumed. Schema version 10 adds immutable class-subject/term policy snapshots, frozen enrollment rosters, editable draft component scores, and append-only score-change history. The generic baseline calculates a points ratio, leaves results incomplete when any component is missing, rounds display percentages to two decimal places using half-up, and selects grade bands with the unrounded percentage. Grade thresholds remain school-configured and are not seeded. Schema version 11 adds administrator approval locks for complete result sets and reasoned post-approval corrections. Schema version 12 adds an administrator-managed school profile for school identity and optional report signatories. Schema version 13 stores an optional size-limited PNG/JPEG school logo in the local database so it travels with database backups. Schema version 14 adds admin-managed fee types and class/session/term fee schedules with canonical decimal amounts and optional due dates. Schema version 15 adds administrator-created draft invoice batches and immutable invoice/line snapshots of enrollment identity and scheduled fee amounts. Only enrollments overlapping the selected term are included; partial-term enrollment is flagged for review and never automatically prorated. Draft batches require a reason to cancel and remain stored; cancelled drafts permit a replacement batch. Schema version 16 adds explicit invoice issuance, immutable payment receipts allocated to one invoice, exact partial payments, derived balances, and immutable reasoned partial/full reversals. Payments require issued invoices; overpayments are rejected and issued batches cannot be cancelled. Date-scoped reconciliation reports ledger receipts and reversals by payment method, and exports all events to CSV. Individual receipts can be exported as PDF with school identity, invoice snapshots, receipt details, reversals, and invoice balance at export time. These exports describe the local ledger and do not verify external settlement. An administrator can import a generic statement CSV with `date,amount,reference,description` columns for read-only matching. Positive amounts represent credits and negative amounts represent reversals. A supplied reference must match the internal reference or receipt number; date/amount-only matches are automatic only when unique. Ambiguous and unmatched rows are exported for review. Statement import is capped at 5 MiB and 20,000 rows and never changes financial records. Reconciliation report access is administrator-only; the UI limits rendered events to 500 while CSV export retains the full date range. Assessment approval, score changes, attendance, timetable, enrollment, profile updates, fee setup, invoice issuance, payment and reversal, and their audit rows use immediate SQLite transactions. No component weights, absence rules, fee proration, currency, or ranking policy are inferred.

Schema version 17 adds a school type setting (Primary, Secondary, or both) and a current-term marker that allows one active term per academic session. Administrators explicitly choose the active session and active term from Academic Calendar; selector data prioritizes those choices. Class-stage setup enforces the selected single-school type for new assignments and flags incompatible legacy stages for manual correction without changing them automatically. Schema version 18 adds a unique optional teacher-login-to-staff link. Teacher grade-entry queries and writes are scoped to that identity's assigned class-subjects; attendance session/class choices and service reads/writes use the same assignment scope. Approvals and approved-result corrections remain administrator-only. Legacy teacher accounts are not linked automatically.

Legacy class mapping is a separate explicit action: an administrator previews one exact legacy value, selects a destination class/section, session, and date, then confirms the group. Only active students are included; any active-enrollment conflict rejects the entire operation. A single `INSERT … SELECT` and mapping audit event commit atomically, while the source class text stays unchanged. This avoids guessing historical mappings and avoids per-student UI-thread work.

Class promotion reuses the session enrollment model without a schema change. Administrators select source and destination sessions/classes and a destination date, review candidates, and may deselect eligible students. Inactive students and any student with destination-session enrollment history are excluded. The selected destination enrollments and their audit events commit in one transaction; source enrollments are retained unchanged. Promotion never infers grade-to-class mapping.

Schema version 22 adds optional student NIN, date of birth, and email fields with an additive migration; existing rows receive blank values and remain unchanged. Student imports validate optional values before committing the roster.

## Presentation and packaging

`theme.py` is a Qt-free design-token module that builds one application stylesheet; `ui_polish.py` installs it app-wide and tidies tables on first show. Dashboard and setup-guide data come from the read-only `dashboard_data.py` so the UI stays thin. `version.py` is the single version source for the installer build in `packaging/`. The installer never writes to `%LOCALAPPDATA%\SmartSchoolManagerRebuild`.

## Compatibility

Preserve existing table data with additive migrations unless removal is explicitly requested. Any table rebuild or destructive removal requires a documented migration plan, verified pre-upgrade backup, recovery path, and clear upgrade path. Keep the original installation and its database entirely separate.

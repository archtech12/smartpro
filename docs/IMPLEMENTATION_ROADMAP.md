# Implementation roadmap

## Phase 0 — Audit and architecture

Completed: repository audit, architecture boundaries, feature status matrix, and roadmap/security model.

## Phase 1 — Stabilize foundation

Completed and verified: versioned schema, verified pre-migration copy, foreign-key verification, SQLite transaction/connection lifecycle, login delays, active-admin authorization for write services, safer password-hash parsing, local rotating logs, and temporary-database tests. Generic record creation and deletion now validate the administrator, mutate the record, and write the audit event in one SQLite transaction. A synthetic-database backup/restore drill also verifies and reopens a separate restored file without changing the source or active database. Still needed: complete login/logout/session handling and native operational restore review.

## Phase 2 — School and academic records

Implemented: version 2 adds `academic_sessions` and `terms`; version 3 adds `student_enrollments`; version 4 adds session-specific class-subject assignments with an optional active teacher. Version 17 adds an explicit active term per academic session and a Primary/Secondary/combined school type in School Profile. Version 18 adds an explicit, unique teacher-login-to-staff link. Administrators can set the current session and term from Academic Calendar; workflows prioritize those choices in their selectors. Class-stage setup enforces a single-stage school selection for new assignments while preserving existing mismatches for manual correction. Student registration supports both a guided single-student form and a validated, atomic class roster CSV import. Admin workflows also support class transfer with retained history, completion, withdrawal, and preview-first class roster promotion between explicitly selected sessions/classes. Promotion identifies inactive students and destination-session conflicts, allows the administrator to choose eligible students, creates destination rows atomically, and preserves source enrollments. Class subject setup and teacher-account management are also available. Legacy `students.class_name` values are preserved; mappings require explicit administrator confirmation.

Student registration is now a guided workflow from the Students screen: the administrator enters the student's names, optional guardian contact, NIN, date of birth, email, and photo; chooses a class/section and academic session; and the app generates an admission ID. Creating the student and their first enrollment is one transaction; a failure leaves neither record behind. A preview-first CSV workflow can register up to 2,000 students into one selected class/session/date; all rows are validated before confirmation and the whole roster commits atomically. The generated ID format is `ADM-<enrollment year>-<sequence>`. Schema v22 adds optional NIN, ISO date of birth, and email columns without changing existing student records.

### Phase 2 status and handoff

Completed: background-loaded review and administrator-confirmed mapping of exact legacy class values; mappings preserve source text and reject conflicted groups atomically. Session-specific class-subject assignments allow one subject per class and session, with an optional active teacher. Bulk assignment can now apply one active teacher to the newly selected subjects in the same step; it leaves existing assignments untouched, and individual assignments remain editable. Schema v5 supports ordered assessment components with decimal maximum points; v6 adds explicit Primary or Secondary class stage; v7 adds editable grade thresholds per academic session and stage without seeded labels. Existing classes are preserved without inferred stage and need administrator assignment. The initial v5-v7 setup work did not include score capture; Phase 3 now adds it. See [ASSESSMENT_POLICY.md](ASSESSMENT_POLICY.md) for the generic rule and deferred decisions.

## Phase 3 — Assessment and results

Implemented slices: Grade Entry now creates editable CA Score (40) and Exam Score (60) starter components on the first administrator load of a class-subject/term when none exist; names and maxima can be changed in Assessment Setup before saving. Component setup remains scoped to a session-specific class-subject assignment and term. Explicit Primary/Secondary class stages and administrator-managed grade thresholds per academic session and stage are supported. Schema v10 adds generic points-based draft score entry with exact decimal validation, incomplete results for missing components, two-decimal half-up display, unrounded grade-band selection, immutable policy and roster snapshots, and append-only score-change history. Schema v11 adds complete-set approval/locking and reason-required administrator corrections with old/new values in history. Grade thresholds remain school-configured with no seeded scale. Grade Entry exports a roster-specific CSV template and validates a full score-file preview before populating the draft table; admission number is the matching key, blank cells preserve current values, and saving remains an explicit separate action. Schema v18 enables linked teachers to load and save drafts only for their assigned class-subjects; administrators retain approval and approved-result correction authority. The teacher workspace exposes only Grade Entry. Remaining: define a school-authorized reopen and reapproval lifecycle before implementing it, and complete broader native Windows role-based review. See [ASSESSMENT_POLICY.md](ASSESSMENT_POLICY.md) for the generic rule and deferred decisions.

## Phase 4 — Reports

Implemented: approved individual report cards, a class PDF with one report card per student page, one-subject class result sheets, and class master sheets. Report cards require complete approved results across all assigned subjects; the class PDF additionally requires a consistent frozen roster. Optional PNG/JPEG student photos can be attached during registration or managed from the student register. Student photos are stored locally in the offline database with a 1 MB limit. School Profile settings provide optional identity, logo, and head/class-teacher signatory text. Report cards and master-sheet rows show an overall average: the equal-weight mean of the student's subject percentages, calculated exactly and displayed half-up to two decimals, and only when every assigned subject is complete and approved. They also show the average's grade (exact average through the school's bands, only when every subject froze identical bands) and class position (exact average, equal averages share a position and the next is skipped, "out of" is the frozen roster size), only after every assigned subject is approved with matching rosters. A School Profile setting (schema v23, default position) chooses whether report cards print class position or the average grade; the class's explicit Primary/Secondary stage, a grading key from the school's bands, and optional class-teacher and head-of-school signature images (PNG/JPEG, 1 MB) also print. Each report card is one A4 page: the layout tries font/padding steps from 9 pt down to 6 pt, then drops the remark column, and a card that still cannot fit is refused instead of splitting across pages. Remaining: handling of withdrawn students, cumulative or annual positions, term closing and next-term dates, psychomotor/affective ratings and an attendance summary on the card, and a native Windows print review. Automated synthetic PDF verification confirms one output page per student. Remaining: native Windows visual review and school confirmation of report-card contents/signatory wording.

## Phase 5 — Attendance and timetables

Implemented slices: version 8 daily attendance registers are scoped to session, class, and date; marks are explicit Present or Absent, unmarked students remain distinct, and corrections require a reason with append-only history. A date-range summary reports enrolled, present, absent, and unmarked counts separately. Administrators can manage any register; linked teachers can read, summarize, and record attendance only for classes where they have a class-subject assignment in the selected session. Service reads and writes recheck the active login, staff link, and assignment; teacher corrections require a reason and remain in append-only history. Version 9 provides session-scoped timetable slots based on existing class-subject assignments. Weekdays and 24-hour times are explicitly entered, and service checks prevent class, assigned-teacher, and named-location overlap. There are no assumed bell times or school-week defaults. Writes and audit events are atomic. Remaining: school-approved late/excused statuses and native Windows visual review. Session timetable PDF printing is implemented.

## Phase 6 — Fees and payments

Slices 1–6 complete: schema v14 adds admin-managed fee types and exact-decimal schedules scoped to class, academic session, and term, with optional due dates, archival rather than deletion, validation, and atomic audit writes. Settings > Fee Setup implements this configuration workflow. Schema v15 adds administrator-generated draft invoice batches from term-overlapping enrollments and active schedules, with immutable student, fee, and amount snapshots. Enrollments covering only part of a term are flagged for review; no automatic proration is applied. Draft batches can be cancelled with a required reason and retained for audit, after which a replacement draft may be generated. Schema v16 adds explicit batch issuance, payment receipt records, exact partial allocations to one invoice, derived balances, and reasoned partial/full reversals. Receipts and reversals are immutable and audited; collection is blocked until the batch is issued, overpayment is rejected, and issued batches cannot be cancelled. Main > Fee Invoices supports background preview, draft creation, issue, single-form payment recording, cancellation, reversal, receipt PDF export, and all-class/all-term or single-class/single-term balance filters within a selected session. Student, admission number, and invoice search filters both balance rows and receipts; visible totals summarize expected, paid, and due amounts. Invoice generation still requires one specific class and term. Main > Transaction History reports date-scoped receipts and reversals by method, exports ledger events, and compares an imported statement CSV against the ledger without writing to financial records. The template uses `date,amount,reference,description`; credits are positive and reversals are negative. A supplied reference must match the saved payment reference or receipt number; otherwise an exact date/amount match is accepted only when unique. Ambiguous matches remain flagged. The import is limited to 5 MiB and 20,000 rows. This comparison does not prove bank settlement, and bank-specific file formats still need mapping to the generic template. Reconciliation output is administrator-only and displays at most 500 rows; exports include the full result. No currency is assumed. Schema v24 and the Fee Setup/Fee Invoices updates add: one fee applied to one class, all classes, or selected classes in a single atomic, non-overwriting save; an administrator-only student statement through the active term (unpaid earlier terms and sessions carry forward, fully paid terms add nothing, later-term invoices are excluded); and a lump-sum payment allocated oldest-first across that student's outstanding issued invoices under one receipt number, with overpayment rejected and each allocation reversible with a reason. Remaining gaps include cross-session student-first search, session-wide annual fee schedules (the billing term for an annual fee is a school decision), automatic invoice generation on term change, and fee statistics. CSV exports open in Excel; a native Excel workbook export remains. These should be designed while retaining invoice issue controls, immutable receipts, and reasoned reversals. Remaining: school review of local collection practices and statement comparison; decide school-configurable currency label and the listed workflow gaps without assuming a currency or annual billing rule.

## Phase 7 — Examination and CBT foundation (deferred)

No examination or CBT workflow is currently available. The Question Bank UI, application services, and active database table were removed at the user's request. Schema v21 removes the table during upgrade after creating a verified pre-migration backup. Revisit this phase only when requested. Any future local-network CBT requires separate threat modeling; do not add networking to the offline core.

## Phase 9 — Operations

Partial: administrator-only online backup creation, integrity/foreign-key/schema-ledger verification, and restore to a separate new database file are available; existing files and the active database are not overwritten. Synthetic backup/restore tests cover reading the restored file through the app connector and writing to the restored copy independently. Set `SMARTSCHOOL_DATA_DIR` for one launch to open a restored copy; startup rejects an override folder missing `school.db`. This keeps the default data location separate and avoids replacing it. Grade Entry supports validated, roster-matched score CSV import, and student registration supports validated preview-first class roster CSV import with atomic student/enrollment creation. Generic CSV exports neutralize spreadsheet formulas. Still needed: native operational restore review, validated general record imports, and administrative reports. Read-only database diagnostics now run SQLite quick-check, foreign-key, and migration-ledger checks on a background worker.

Initial responsiveness work debounces list searches, loads record/enrollment pages in background workers, limits rendered pages to 200 rows, and runs CSV export, dashboard counts, authentication, and normal UI writes in background workers. A searchable student lookup avoids building a combo box containing every student. Dashboard shortcuts provide direct access to implemented record and academic setup screens. Database initialization and migration backup run in a worker while a startup progress dialog remains responsive. Main-window pages are now constructed on demand instead of opening database-backed screens at startup; each page's initial load is not duplicated during navigation. A synthetic 20,000-student/20,000-enrollment profile on the current machine measured first-page student listing at 2.36 ms median, a page at offset 10,000 at 3.30 ms, broad student search at 27.03 ms, searchable lookup at 27.97 ms, first enrollment page at 18.84 ms, enrollment page at offset 10,000 at 39.75 ms, and dashboard counts at 2.95 ms (five timed repetitions per operation). CSV export of the 20,000 synthetic students took 91.07 ms median over three runs (about 859 KiB). An exclusive SQLite lock made a page request wait 7.06 seconds before timing out with the original 5-second connection timeout; the connection wait is now capped at 2 seconds and a regression test confirms the lock error is returned within 4 seconds without changing records. Database operations remain in background workers, so this wait does not block the Qt event loop. An offscreen PyQt6 smoke check also constructed the main window, navigated all 17 database-backed pages against an isolated synthetic database, and waited for their background workers to finish. Windows CIM hardware details were inaccessible in this environment, so neither the machine's performance tier nor low-spec behavior is verified; the offscreen check does not replace a native Windows visual review. The next useful device-specific check is a low-spec Windows run measuring app startup and page rendering.

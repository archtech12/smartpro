# Feature matrix

Status meanings: **Implemented and tested** means automated verification was run; **implemented, testing incomplete** means code exists but adequate automated verification is absent; **partial** means only part of the workflow exists; **not implemented** means no functional implementation exists.

| Area | Status | Evidence / limits |
|---|---|---|
| First-run administrator and sign-in | Partial | Offscreen first-run and sign-in smoke passed; persistent progressive delay exists. No lockout reset/admin recovery workflow or native desktop review. |
| Role-based access | Partial | Schema v18 links a teacher login to one staff record. Teachers see a grade-entry-only workspace; grade reads and draft writes are scoped to their assignments. Account management, approvals, corrections, and other school workflows remain administrator-only. No principal workflow. |
| Password storage | Implemented and tested | PBKDF2-HMAC-SHA256 and constant-time compare; encoded work factor and digest lengths bounded. Correct, wrong, and malformed hashes tested. |
| SQLite persistence | Implemented and tested | Parameterized values, foreign keys, timeout, transaction rollback and connection close handling. Suite passed. |
| Versioned migrations | Implemented and tested | Versions 1 through 22 plus integrity-checked copy before upgrading an existing DB. Version 22 adds optional student NIN, date of birth, and email fields while preserving existing rows. Tests cover upgrade preservation, migration rollback, and backup-copy failure; full restore drill remains. |
| Audit trail | Partial | Login, generic CRUD, session, term, enrollment, class-stage, subject-assignment, and assessment-setup events exist. Generic CRUD audit events commit atomically with mutations; no user ID FK, tamper protection, or full event-coverage review. |
| Student records | Partial | Guided registration collects names, optional guardian contact, NIN, date of birth, email, and optional local PNG/JPEG photo, lets the user select a class/section and academic session, generates a unique admission ID, and atomically creates both the student and first enrollment. Student Register supports viewing a background-loaded read-only profile with photo, enrollment history, approved results, attendance totals, and fee invoices/balances. Preview-first CSV/Excel import validates up to 2,000 roster rows before an atomic student/enrollment save into one selected class and session; it accepts `full_name` or first/last name columns, preserves supplied admission numbers, and generates missing ones. Student exports include admission number. Search/export, transfer, completion, withdrawal, preview-first promotion, and administrator-only archive/restore are available. Existing class text is preserved without inferred mapping; general record imports remain absent. |
| Teacher/staff records | Partial | Staff CRUD/search/export and class-subject assignment are available. Administrators can create/link teacher logins; each login can link to one active staff record. Teacher accounts can enter drafts only for their own assigned class-subjects. Staff reports and workload validation are absent. |
| Classes and subjects | Partial | Classes now have explicit Primary or Secondary stage, assigned through an audited admin workflow; unclassified classes cannot receive subject assignments or mapped enrollments. Subjects can be assigned per session with an optional active teacher; bulk assignment can apply one active teacher to the newly selected subjects, while existing assignments remain unchanged. One subject assignment per class/session is enforced. Custom stage labels, session-specific class creation, and teacher workload validation are absent. |
| Academic sessions and terms | Implemented and tested | Version 2 schema with version 17 current-term support. Administrators can create/edit sessions and terms, explicitly set one active session and one active term per session, and see their status in the calendar. Date-range validation, term ordering, atomic audited status changes, and active-first workflow selectors are covered. |
| School profile and type | Partial | Optional school identity, signatories, and logo are stored locally. Version 17 adds Primary, Secondary, or combined school type. Class-stage setup enforces that selection for new assignments and offers correction of existing mismatches without altering records automatically. Version 19 adds optional locally stored student photos for report cards. |
| Student enrollment history | Implemented and tested | Version 3 links students, existing classes/sections, and sessions; one active enrollment per student/session; transfer preserves both rows; completion and withdrawal close active rows. Preview-first promotion explicitly creates destination-session enrollments in one class and preserves source rows. No historical class values are auto-mapped. |
| Report cards and results PDFs | Partial | Approved individual report cards, class result sheets, and master sheets are available. The class report-card PDF now produces one approved report page per student with optional student photo, school logo, and configured signatory names/titles; PDF output is tested on synthetic data. Native Windows visual review and local school confirmation remain. |
| Legacy class review and mapping | Implemented and tested | Background-loaded summary and administrator-confirmed mapping of one exact legacy value to an explicit class/section, session, and date. Active students only; existing active enrollment conflicts block the whole group; inserts and audit are atomic. Tests confirm source values are preserved. User should verify the mapping UI on synthetic records before using real school data. |
| Dashboard and setup guide | Implemented, testing incomplete | Admin dashboard shows current session/term, counts, explicit boys/girls/other/not-recorded demographics, today's attendance, issued invoices and draft batches for the term, results awaiting approval, and up to five leading students from complete, approved, roster-consistent current-term results (read-only, background-loaded; no currency or amounts). Achiever averages reuse report-card equal-weight subject averages. A setup guide checks ten required steps (profile, session/term, classes, stages, subjects, class subjects, grade bands, assessment setup, students, enrollments) and two optional ones (teacher accounts, fees), shows progress, and opens each page; it is offered once on a brand-new school. Data logic is tested (`tests/test_dashboard_data.py`); Qt screens are covered by tests that need PyQt6 and a native Windows review. A guided first-run wizard that edits data inside the guide is not implemented. |
| Communication Center | Implemented, testing incomplete | Schema v25: editable templates, outbox/history, guardian opt-outs, country-code setting. Birthdays, fee reminders (uses issued-invoice balances through the active term), outbox with open-in-mail/WhatsApp or copy then mark sent, history with CSV export, statistics. Nothing is sent over a network. Announcements and attachments are not built. Data logic tested in `tests/test_communications.py`; Qt screens need a native Windows review. |
| Account security and audit | Implemented, testing incomplete | Every role can change their own password (current password required). Administrators have a read-only audit log viewer with date/action/search filters and CSV export. Data logic tested in `tests/test_account_audit_terms.py`. |
| Visual design | Partial | One shared stylesheet (`smartschool/theme.py`) is applied app-wide, including dialogs and message boxes; sidebar shows the active page, a page filter (Ctrl+K), top bar with page title, Refresh and F5; tables get alternating rows and clipped-cell tooltips on first show. Written without a display: needs a native Windows visual review. Per-page layout polish, empty-state messages and inline validation remain. |
| Logging | Partial | Rotating local file logging configured at UI startup; startup exercised, coverage and error presentation need expansion. |
| Backup and restore | Partial | Administrators can create and verify online SQLite snapshots and restore one into a separate new database file. Verification checks SQLite integrity, foreign-key references, and schema history; existing files and the active database are never overwritten. Synthetic-database restore drill confirms the restored file opens through the application connector and can be used independently. An explicit process-scoped `SMARTSCHOOL_DATA_DIR` override opens a restored copy, and startup refuses to create a blank database when that override points to a folder without `school.db`. Read-only administrator diagnostics check integrity, foreign keys, schema history, disk space, and record counts in the background. Scheduling, retention, and native operational restore review remain outstanding. |
| Assessment setup and grade entry | Partial | On the first administrator load of a class-subject and term with no components, Grade Entry creates CA Score (40 points) and Exam Score (60 points) so the class roster is immediately ready for entry. Schools can edit these names and maxima in Assessment Setup before saving scores; headers show the configured maxima. Grade thresholds and remarks are school-configured per academic session and Primary/Secondary stage with no seeded defaults. The Class and subject dropdown contains existing combined class-subject assignments for the selected session; if empty, the screen explains that class stage, subjects, and Settings > Class Subjects assignments must be configured first. Selecting a session, class-subject, and term automatically loads active students whose enrollment overlaps the term. CSV/Excel templates and validated import use student admission number, name, and compact component headers such as `MTH_CA`, `MTH_EXAM`; preview precedes draft entry and Save remains explicit. Admin entry and linked-teacher assignment-scoped draft entry snapshot policy and roster; complete sets can be approved and locked; post-approval admin corrections require a reason. Reopening remains unimplemented. |
| Report cards and result sheets | Partial | Administrator can export one individual report card or one class-wide PDF with exactly one report-card page per student, plus one-subject class result sheets and class master sheets. Reports require complete approved results; class PDFs also require consistent frozen rosters. Optional student photos, school logo, identity, and signatory text are included. Each report card and master-sheet student shows an overall average (equal-weight mean of subject percentages, complete approved results only). Reports also show the overall average and, per the School Profile setting, either class position (shared position on ties, next skipped) or the average grade. Each card is exactly one A4 page that tightens its layout for 20+ subjects, shows the Primary/Secondary stage and a grading key, and can carry class-teacher and head signature images. Automated synthetic PDF check passed; native Windows review and school confirmation remain. |
| Attendance | Partial | Session/class/date register with explicit Present/Absent marks, unmarked kept distinct, reason-required corrections with append-only history, and atomic audit. A date-range summary keeps enrolled, present, absent, and unmarked counts distinct. Administrators can manage all registers; linked teachers are limited in service reads and writes to classes assigned to them in the selected session. Late/excused statuses and native Windows review remain. |
| Timetable | Partial | Version 9 session-scoped slot editor uses class-subject assignments and explicit weekday/start/end times; class, assigned-teacher, and named-location overlaps are rejected. Admin-only writes and service tests plus offscreen save/render smoke passed. Session timetable exports to landscape PDF with configured school identity. No default period/week pattern is imposed; native Windows review remains. |
| Fees/payments/receipts | Partial | Schemas v14–v16 provide term/class/session fee schedules, immutable draft invoices, issuance, partial payments to one invoice, unique receipts, derived balances, reasoned reversals, receipt PDFs, date-scoped reconciliation, and read-only comparison against a generic cash/bank statement CSV. Fee Invoices separates student balances, payment history, and per-class balances; totals count issued invoices only and show draft counts separately. Payment entry is a single invoice-context form. Transaction History reports and exports date-scoped receipts and reversals. Fee Setup can apply one fee to one class, all classes, or selected classes in one atomic save. A student statement shows balances through the active term (earlier unpaid terms carry forward) and takes one lump-sum payment allocated oldest-first under one printable receipt. Cross-session student search, whole-session annual schedules, fee statistics, and Excel workbook export remain. CSV exports open in Excel. Bank-specific formats and local school policy review remain outstanding. |
| Examination/CBT | Not implemented | The Question Bank module and its application workflows have been removed. Schema v21 drops its table from the active database during upgrade; the verified pre-migration backup retains a recoverable copy. No exam or CBT workflows are currently available. |
| Parent communications/integrations | Not implemented | No functional workflow. |
| Windows installer | Implemented, not yet built on Windows | PyInstaller one-folder spec, Inno Setup script (per-user install, in-place upgrades, uninstall keeps `%LOCALAPPDATA%` school data) and `packaging/build_windows.ps1` (runs tests first). Inputs are guarded by `tests/test_packaging.py`. The installer has not been built or run; code signing is not set up. See `docs/PACKAGING.md`. |
| Automated tests | Partial | Foundation, calendar and active session/term selection, school type, guided and bulk student registration, student/score CSV validation, enrollment, class-stage, class-subject, assessment-component, grade-band, fee setup, draft grade entry, result approval/correction, backup, attendance summary, and timetable tests cover foundational services and selected UI flows. Coverage is limited to these foundations; other domain workflows still need broader verification. |
